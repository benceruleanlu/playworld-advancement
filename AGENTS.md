# Agent and contributor notes

Hackathon repo: raise an open world model's PlayWorld score above Genie 3 (2.12). The track allows fine-tuning and forbids training from scratch; we change only how the model is run at inference time, a choice made for time (see "Plan of record"). Project docs live in this file (README.md is the public landing page); do not add a docs/ directory.

## Layout

- `third_party/PlayWorld/` upstream benchmark, pinned submodule. No license: import or subprocess it, never copy its code into this repo.
- `adapters/<name>/run.py` world-model runners. They reuse the upstream closed-loop harness and swap in our engine.
- `pwa/` iteration CLI (`pwa --help`).
- `splits/` dev (24) / heldout (147) / all (171) task lists. Regenerate with `splits/make_splits.py`; do not hand-edit.
- `runs/<exp>/` rollouts, verifier output, logs (git-ignored).
- `results/experiments.csv` shared experiment log (committed).
- `research/` working notes behind the plan: baseline census, red-team rulings and plan, autoresearch loop study, out-of-sight analysis (`research/README.md` indexes them). Plan of record: issue #9.

## Rules

- New experiment name for every run. Upstream `--skip-done` silently reuses old videos; `pwa gen` refuses existing dirs unless `--resume`.
- Iterate on `dev`. Do not score `heldout` before code freeze.
- Final numbers must be closed loop (`--action-source agent` or `refined`) and scored with Gemini 3.1 Pro at the upstream sampling settings. `--action-source dataset` is for fast A/B only.
- Do not change verifier FPS, resolution, or JPEG settings.
- For a reported claim, a delta smaller than 2x the pass-to-pass std is noise.
- For dev decisions use the adoption rule ("Plan of record"): a task cell moves only at a full point on the mean of its judge passes, and a flag is adopted only if the gain repeats on both seeds and no gate that passed in the baseline fails (`pwa cells` gives the readout).
- Screening judge (`--judge-model`, e.g. `gemini-4-hydrogen`) is for dev loops only: picking which arm deserves an official run. The official judge (Gemini 3.1 Pro, upstream settings) decides what ships and produces every reported number. Never quote, plot or compare a screening score against the leaderboard or against an official score.
- Secrets live in `config/env.sh` only. Never print or commit key values.

## Skills

`.claude/skills/` holds skills copied from [jpoehnelt/skills](https://github.com/jpoehnelt/skills) at commit `0eefeee` (MIT, see `.claude/skills/LICENSE`). The set is `eng-*` (change checklist, blast radius, benchmark checklist, testing, TDD, agent CLI scale), `gh-*` (CI triage, PR feedback loop, PR commit review), `comms-*` (technical writing, unslop, impact, how, why, interrogate, slides) and `agents-*` (correct, reflect, swarm). To update a skill, copy its folder again from upstream. The skills read these repo facts:

- Tests run with `python -m pytest -q` from the repo root. Run one file with `python -m pytest -q tests/test_cli.py`. Build the site with `cd site && npm ci && mkdir -p public && cp ../results/experiments.csv public/ && npm run build`.
- `.github/workflows/ci.yml` has two jobs. `test` runs pytest and needs the PlayWorld submodule and the dataset JSON from Hugging Face. `site` builds the Astro site. `experiment.yml` runs only when started by hand and needs the repo secrets and Modal. `pages.yml` deploys the site on pushes to main.
- `tests/fake_runner.py` stands in for a GPU runner in tests. CI does not test GPU generation, Gemini scoring or agent API calls. Those need a person with keys.
- `pwa` is the benchmark harness (see below). A score claim needs a closed-loop run scored by Gemini 3.1 Pro over 2 or more passes, and a delta of at least 2x the pass std (`pwa compare` checks this).
- The repo has no PR template or changeset. PR and commit titles use `Area: what changed`, for example `Site: ...` or `lingbot: ...`. Squash merges append the PR number.

## CLI (`pwa`)

Setup: `./setup.sh`, fill `config/env.sh`, `source .venv/bin/activate`, `pwa doctor`.

- `pwa doctor [--for gen|score|all] [--runner R] [--json]` check env, data, keys, model roots, torch/cuda.
- `pwa tasks [--split dev|heldout|all|PATH] [--family ..] [--json]` list tasks.
- `pwa gen EXP --split dev --runner sana|NAME|PATH --action-source dataset|agent|refined [--shard i --num-shards n] [--resume] [--notes ..] [--max-chunks N] [-- runner args]` rollouts to `runs/EXP/videos/`, plus `meta.json`, `gen.log`.
- Capped smoke tier: `pwa gen ... --action-source agent|refined --max-chunks N` passes upstream's own `--num-chunks N` to the runner (run_agent bounds a closed-loop rollout at `min(--num-chunks, frame budget)`, default 30; wait-only insight tasks honour it too). Refused with `--action-source dataset` (one long rollout, no chunks) and together with `-- --num-chunks`. `meta.json` records `max_chunks` and a `label`; a resume must repeat the same cap. A run is capped if `max_chunks` is set or its runner args carry `--num-chunks` below 30 (`core.chunk_cap`). Capped runs are labelled everywhere: `pwa report` text and `--md` banner, report JSON `max_chunks`, the csv `max_chunks` column and a `[capped smoke: N chunks]` notes prefix, the Scenes manifest, and the site ("capped smoke, N chunks" badge; never the headline, ruler, family bars, best-so-far line or a final score). `pwa compare` warns when two runs have different caps.
- `pwa gen-arms EXP --arms ' | --lingbot-turn-cal' [same selection and gen flags] [-- args for every arm]` several arms (runner arg strings separated by `|`; an empty one or `base` is the baseline, at most 8) on one task list, back to back in one process. Arm i is an ordinary experiment `EXP-a<i>` (its own `meta.json` with `arm_group`/`arm`/`num_arms`/`arm_args`, `gen.log`, videos; notes get `[arm i/N of EXP: args]`, where args are every arg the arm ran with, the shared `--` args first; `base` only when there are none). `--arms VALUE` and `--arms=VALUE` both work, also for a value starting with `--`. The runner's `main(argv)` is called in process instead of one child per family, so it needs a runner with a `__main__` guard and `main(argv)` (`lingbot_world2`, `lingbot_world2_1p3b`, `tests/fake_runner.py`); the upstream SANA runner is refused. Output a runner's own child processes write to fd 1/2 (ffmpeg) reaches the container log but not `gen.log`. Exits 1 if any arm has a failed task or runner error; the other arms' videos are still written. `python -m pwa.arms EXP ARMS [SHARED]` prints one `NAME I/N LABEL` line per arm.
- `pwa score EXP [--passes 2] [--workers 4] [--dry-run] [--force]` verifier into `runs/EXP/eval/pass<k>/`; idempotent.
- `pwa report EXP [--split ..] [--strict] [--json] [--md [--site-url U]]` per-family means, std, gate passes, missing; upserts `results/experiments.csv`.
- `pwa compare A B [--json]` deltas B minus A, flags noise (< 2x pass std).
- `pwa cells A B [--json]` per-task pass-means of A and B on their shared tasks, the delta, and how many tasks moved up or down by at least 1.0 (a cell moves only at a full point). The decision readout for an A/B.
- Screening judge: `pwa score|report|compare|cells|failures ... --judge-model MODEL [--judge-thinking minimal|low|medium|high]` runs or reads the same upstream verifier with `--model MODEL`, in `runs/EXP/eval-<slug>/pass<k>/` (slug = model id with characters outside `[A-Za-z0-9._-]` replaced by `-`, plus `-think-<level>` with a thinking level). Output is labelled "screening judge: MODEL, not comparable to the leaderboard"; `report` writes `report.<slug>.json`, never `report.json` or `results/experiments.csv`. Without the flag nothing changes (`$GEMINI_MODEL`, default `gemini-3.1-pro-preview`, `eval/`). Upstream `metrics/vqa/score.py` passes the model id through unchanged (no allowlist) and sets no thinking config (only `response_mime_type` and `temperature=0.1`), and no env var sets one; `--judge-thinking` runs it through `pwa/judge_shim.py`, which adds `thinking_config` to that config object and leaves the submodule untouched. Dry runs (`--dry-run`) call no model and keep writing `eval_dry/`.
- OpenAI-compatible screening judge: `--judge-model openai:MODEL[:THINKING]`, e.g. `openai:gpt-6-luna` (a plain name or `gemini:` stays Gemini; a trailing `:minimal|low|medium|high` is the thinking level, the same as `--judge-thinking`). Slug `openai-MODEL[-think-L]`, so `runs/EXP/eval-openai-gpt-6-luna/`. It runs the same upstream `metrics/vqa/score.py` through `pwa/judge_shim.py`, which replaces `metrics.gemini_client.create_gemini_client` with `pwa/judge_openai.py`: upstream still samples the frames, builds the contact sheets, writes the prompt and parses and writes the JSON; only its `generate_content` call goes to `POST {JUDGE_API_URL}/chat/completions` (text parts in order, images as `data:` URIs with `detail: high`, `response_mime_type` JSON as `response_format: json_object`, `temperature` 0.1 as upstream, thinking as `reasoning_effort`). Upstream records `gemini_model: openai:MODEL`. Key and URL: `JUDGE_API_KEY` / `JUDGE_API_URL`, falling back to `PLAYER_API_KEY` / `PLAYER_API_URL` (URL fallback only when the player provider is openai; default `https://api.openai.com/v1`). The verifier process gets a placeholder `GEMINI_API_KEY`, never the real one. Retries: 4 per call on 408/409/429/5xx, timeouts and connection errors (2, 4, 8, 16 s or `Retry-After`, `JUDGE_API_RETRIES`, `JUDGE_API_TIMEOUT_S` 600); then the verifier exits non-zero and `pwa score` writes `<task>_<mode>.err` and retries the call `--retries` times as for Gemini. Error text carries the HTTP status and at most 300 chars of body (none for 401/403), scrubbed of the key. `JUDGE_API_NO_TEMPERATURE=1` drops the temperature up front. Verified on the first real run (experiment run 43662935128, 24 dev videos, 2 passes): the key fell back to `PLAYER_API_KEY` and authenticated, and `gpt-6-luna` rejected all 48 calls with HTTP 400 `param: temperature` ("only the default (1) value is supported"). The client now retries a 400 whose `param` is `temperature`, `top_p` or `seed` once without it (stderr note `model rejects temperature=0.1`) and leaves it out of later calls, so a `gpt-6-luna` screening judge samples at temperature 1, not upstream's 0.1. Other 400s, including one on `reasoning_effort` or `response_format`, still fail. Unverified until a run that gets past the temperature: that `gpt-6-luna` accepts `json_object` and `reasoning_effort`, how the provider resizes the contact sheets (OpenAI scales images itself, so the judge may not see upstream's resolution), and whether its scores agree with the official judge.
- Panels: `pwa score|report|cells ... --judge-model A --judge-model B` (repeat the flag; `--judge-thinking` only with one judge). `score` scores each judge in turn. `report` writes `report.<slug>.json` per judge and prints each task's mean under every judge and the spread. `cells` prints each judge's A, B and delta per task, `agree` (every judge's delta has the same sign) and the panel move: a task moves only if every judge moves it the same way by 1.0. `compare`, `failures` and `run` take one judge.
- `pwa judges EXP --judge-model A [--judge-model B] [--json] [--md]` calibration on one experiment that has official scores (`eval/`) and screening scores on the same videos: per screening judge, tasks scored by both, Spearman rank correlation with the official per-task means (average ranks for ties), mean absolute difference, mean bias (screening minus official), count and ids of tasks 1.0 or more off official, and self-agreement between its own passes (mean pairwise difference, pass 1 vs pass 2 Spearman, tasks whose passes spread by 0.5 or more), with the official judge's self-agreement as the reference row. Writes nothing. All panel and calibration output is labelled "screening, not comparable to the leaderboard"; none of it touches `eval/`, `report.json` or `results/experiments.csv`.
- `pwa media EXP --out DIR [--base-url URL] [--release-url URL] [--index PATH] [--screening JUDGE] [--report-name NAME] [--site-url U]` web copies of any run's rollouts (scored or not), the Scenes manifest and `SCENES.md` (every task with a play link); used by the workflow, see "Scenes and attribution".
- `pwa failures EXP [--all] [--json] [--md]` missing, gate-failed, or 1.0 tasks with the verifier's reason; `--all` lists every task.
- `pwa upsert-row EXP --into PATH` copy EXP's row from this checkout's `results/experiments.csv` into another CSV by column name (adds missing columns, fails on malformed files); used by the workflow.
- `pwa mark EXP --into PATH --status running|generated|failed|cancelled [--split ..] [--runner ..] [--action-source ..] [--notes ..] [--max-chunks N]` live status row for a run (score-less); used by the workflow. `running` never overwrites a row that has a score, and the other statuses only update a row that still says `running`.
- `pwa ls [--json]` experiments and status.
- `pwa preview EXP TASK` export the contact sheets the judge sees.
- `pwa run EXP ...` gen + score + report.

Typical loop: run one family of dev tasks per arm (`experiment` workflow, `tasks` input, `num_shards` = number of tasks), the same tasks with a flag on under a new name, then `pwa cells BASE ARM`. Two seeds per arm before adopting anything.

### Adapters

`adapters/<name>/run.py` imports upstream `run_agent`, applies `adapters/common/agent_api.patch` (sets auth by `PLAYER_API_PROVIDER`), swaps `SanaWMEngine` for our engine, and calls `main()`. Wrappers compose around `generate()`, e.g. `AnchorMemory(base_engine)`. `matrix_game3/run.py` is a stub and stays one: the Matrix-Game 3.0 line was dropped (issue #4 closed). `sana_wm` ran a one-task smoke test and SANA-WM work is stopped.

`lingbot_world2` (14B) and `lingbot_world2_1p3b` (1.3B) run LingBot-World v2 causal-fast (PlayWorld paper: 1.82 overall via its web demo). Notes:

- The released code is conditioned on camera poses only; its WASD/IJKL files are never read. `adapters/lingbot_world2/poses.py` turns each key into per-frame camera deltas (signs checked against upstream examples; rotation rates via `LINGBOT_YAW_RAD` / `LINGBOT_PITCH_RAD`).
- Turn calibration, off by default: `-- --lingbot-turn-cal` (Actions input `extra`) or `LINGBOT_TURN_CAL=1`. Dataset tokens are fixed angles in the task prompts ("→*4" = 90 degrees, "u*2" = 40 degrees) but the default 0.03 / 0.01 rad per frame turns 34 / 11 degrees per 20-frame token. The flag sets the rates per call so a token is 22.5 degrees of yaw and 20 of pitch in dataset mode, and a closed-loop chunk is 2 tokens (45 / 40 degrees). Not corrected for tasks whose dataset actions exceed the frame budget and are rescaled by the harness. Unscored; under the plan of record it is evaluated only inside the arms that need it (player hint, GC re-anchor), not as a separate decision.
- Caption prompt, off by default: `-- --lingbot-caption-prompt` (Actions input `extra`) or `LINGBOT_PROMPT_MODE=auto|caption`. The harness gives the engine the agent goal as its text prompt: "wait and observe" on 29 of 30 Insight tasks, camera instructions on Out-of-sight. The flag conditions LingBot on the task's `image_caption` instead (plus the goal for IF, whose goal describes the subject's action), as upstream's Genie 3 and HappyOyster players do; the agent still sees the goal (`adapters/common/prompts.py`). Unscored; adopted only under the adoption rule ("Plan of record").
- Re-anchoring, off by default, session mode only: `-- --lingbot-reanchor` (Actions input `extra`) or `LINGBOT_REANCHOR=1`. `session.ReturnDetector` follows the commanded camera track; when it comes back within 6 degrees and 2 key units of the start pose after leaving (20 degrees or 8 units), that latent of the image conditioning `y` is set to the input image again (mask 1, latent of a still clip), once per visit. GC call names only (`LINGBOT_REANCHOR_TASKS`, a regex), because the Out-of-sight rubric scores a first-frame reset as level 1. The track is the commanded one: rotate-then-walk loops such as GC038 close only with `--lingbot-turn-cal`. Unscored; adopted only under the adoption rule ("Plan of record").
- Player hint, off by default: `-- --lingbot-player-hint` (Actions input `extra`) or `LINGBOT_PLAYER_HINT=1`. Upstream never tells the closed-loop player how far one action turns the camera (default rates: 55 degrees of yaw per chunk, 48 on the first; 45 with turn calibration). The flag appends to the goal the player reads the size of one action and the commanded camera relative to the start (heading, tilt, position, total turned), replayed with `poses.py` (`adapters/lingbot_world2/player_hint.py`). The pose is commanded, not measured from the video. LingBot's own prompt and inputs do not change, and dataset mode and wait-only insight tasks never call the player, so only closed-loop GC, IF and out-of-sight rollouts differ. `gen.log` prints the pose at each decision. Unscored; adopted only under the adoption rule ("Plan of record").
- Return stop, off by default: `-- --lingbot-return-stop` (Actions input `extra`) or `LINGBOT_RETURN_STOP=1`. The GC rubric subtracts up to one point for camera travel after the goal is first complete and accepts a still tail, and the baseline player never stopped after a return. The flag wraps `decide_action` (`adapters/lingbot_world2/return_stop.py`): once the commanded camera has left (0.75 of the largest angle and step count in the goal, on the side and axis the goal names; else 40 degrees or 2 dataset steps) and is back within half an action of the start, the player is not asked again; the wrapper answers WAIT for 2 chunks, then END. Armed only on goals with one return phrase and no "then" after it (36 of 48 GC, 32 of 43 out-of-sight, no IF or insight goals); the rest go to the player unchanged. The pose is commanded, not measured, and the overridden steps are still logged as `source=agent` in `_result.json`; `gen.log` prints `[lingbot] return stop: ...` for each one and the flags line gains `return_stop=on|skip return_stops=N` (only with the flag on). Rollouts get shorter. Read per arm under `pwa gen-arms`; it composes with `--lingbot-player-hint` (a stopped step is not hinted) and `--lingbot-turn-cal` (the replay uses the calibrated rates). Smoke: `arms` workflow, arms `--lingbot-player-hint | --lingbot-player-hint --lingbot-return-stop` (the hint in both arms, because the stop only fires once the player brings the camera home), tasks `GC031,GC033,GC036,OE034,OE058,OE047` (the five dev tasks whose judge reasons name motion after the return, plus OE047, which must show `return_stop=skip`), runner `lingbot_world2_1p3b`, action_source `agent`; check `return_stops` > 0 on the armed tasks and watch the tails before scoring. Unscored; adopted only under the adoption rule ("Plan of record").
- GC completion hint, off by default: `-- --lingbot-gc-completion-hint` (Actions input `extra`) or `LINGBOT_GC_COMPLETION_HINT=1`. On GC tasks only, appends a reminder to the goal the player reads: run the requested camera path once, track which parts the frames show finished, and choose END once every part is visibly complete (`adapters/lingbot_world2/gc_completion.py`). The player's action is forwarded unchanged; nothing is forced. The flags line and `lingbot_flags` JSON add `gc_completion=on gc_completion_hints=N gc_completion_ends=M` (decisions that got the reminder, END replies among them). An alternative arm to return stop; do not combine them in a first A/B. Both flags together are supported: return stop wraps outermost and reads the unmodified goal, so its WAIT/END decisions never reach the player and are not counted here. Smoke: arms `--lingbot-turn-cal --lingbot-player-hint | --lingbot-turn-cal --lingbot-player-hint --lingbot-gc-completion-hint`, tasks `GC031,GC033,GC036`, closed loop, 14B, `stage=gen-only`, `max_chunks=10`, same seed; check that each video completes every requested segment and ends without extra moves. Unscored.
- Flag counters (`adapters/lingbot_world2/flag_stats.py`): after each task `gen.log` gets `[lingbot] flags task=GC033 turn_cal=1 caption=used reanchor=on reanchor_events=2 player_hint=on player_hints=30` (caption `off|used|fallback|none`, reanchor `off|on|skip`), a `[lingbot] flags total ...` line at the end, and the same fields under `lingbot_flags` in `<task>_result.json`. Grep it before scoring: a flag that is on but shows `caption=fallback`, `reanchor=on reanchor_events=0` on every GC task, or `player_hints=0` on closed-loop tasks did nothing. The `[lingbot] mode:` line lists every active flag.
- Default is a persistent session (`adapters/lingbot_world2/session.py`, `reset/step`): the KV cache (LingBot's only memory), noise generator, camera track and VAE decoder cache survive across agent steps. `<task>_chunk_<NN>` following chunk NN-1 of the same task continues; chunk 01, another task or `<task>_full` (dataset mode: reset plus one long step) resets. A/B baseline: `-- --lingbot-stateless` (Actions input `extra`) or `LINGBOT_SESSION=0`, a fresh upstream rollout per call. `LINGBOT_STREAM_DECODE=0` re-decodes all latents per step instead of streaming.
- Session frame accounting: a request of F frames runs n = round((F-1)/16) latent chunks; the first step returns 16n-3 frames (input frame first), later steps the previous last frame plus 16n new ones, so the harness stitch is seamless (default 33 -> 29, then 33). The stateless path rounds up to 4n+1 frames with latent length a multiple of 4 (33 -> 45; `-- --chunk-frames 29` for exact chunks).
- Translation normalisation: upstream divides by the max per-latent translation of the whole sequence, unknown in closed loop. The session divides by a fixed 4 (one latent of straight single-key motion) and clips norms above 1, which equals upstream whenever the fastest latent is straight single-key motion.
- Start-up timing, always on (`adapters/lingbot_world2/fast_start.py`): `gen.log` gets one `[lingbot] timing <part> <s>s` line per load part (`load.import_wan`, `load.t5`, `load.vae`, `load.dit`, `load.dit_to_device_and_rest`, `load.total`) and, after every session reset, `reset.text_encode` (with `source=memory|disk|computed`), `reset.y_encode`, `reset.total`, then `step0.y_encode` (fast-y only), `step0.first_forward`, `step0.denoise_rest`, `step0.decode`, `step0.to_host` for the first step. Read these before changing the fast-start flags' defaults. Timing lines print when a part ends, so the reset also prints `[lingbot] reset: text encode start (t5=cpu|gpu, torch threads=N, disk cache=on|off)` and `[lingbot] reset: y encode start` (full-horizon y only) before those parts: a start line with no timing line after it names the stuck part.
- Stall watchdog, per `generate()` call (`adapters/lingbot_world2/watchdog.py`; Actions input `extra`, env in brackets, read per call in `configure()` like the other flags, so arms never share it). `--lingbot-stall-dump N` (`LINGBOT_STALL_DUMP_S`, default 300, 0 = off): once a call has run N s, every thread's Python stack goes to stderr (faulthandler), and again every N s until it returns, then `[lingbot] stall: NAME returned after Ts`. `--lingbot-stall-abort N` (`LINGBOT_STALL_ABORT_S`, default 0 = off): after N s it prints `[lingbot] stall: NAME still running after Ns`, dumps the stacks and ends the runner process with exit code 124. Env vars do not reach the Modal container; use the args. An abort drops the rest of the runner's work: under `pwa gen` the remaining tasks of that family on the shard (later families still run), under `pwa gen-arms` and warm containers every remaining arm and family on the shard. Those tasks have no mp4, so `pwa gen` exits 1 and the Generate step fails as for any missing task; regenerate them with `--resume`. Under `pwa gen-arms` the stack dumps reach the container log, not `gen.log`. The `[lingbot] mode:` line shows the limits. Suggested for 14B: `--lingbot-stall-abort 900` (the healthy first chunk takes about 2 min). Not yet exercised on a GPU.
- Fast-start flags, all off by default and unscored (Actions input `extra`; env in brackets). `--lingbot-fast` turns on the first three and `--lingbot-fast-dit`. Under `pwa gen-arms` they are read per arm like the other `--lingbot-*` flags: `--lingbot-fast-y` and the T5 disk cache follow each arm, while the load-time parts (read-ahead, meta-built and lazy T5) apply only to the arm that loads the pipe; arms that reuse it skip the load, and the loader patches are undone after the load.
  - `--lingbot-fast-t5` (`LINGBOT_FAST_T5=1`): T5 prompt embeddings cached on the weights Volume (`$LINGBOT_WEIGHTS/t5_cache`, or `LINGBOT_T5_CACHE_DIR`), keyed by sha256 of the prompt plus the T5 checkpoint (name, size, hash of its first and last MiB), tokenizer files, text length, dtype, torch version and where T5 runs (CPU model and thread count, or GPU name). T5 is not loaded at start-up; it loads on the first miss. A hit returns the tensor T5 returned when the entry was written, moved to the GPU. Entries are written during a run and reach the Volume at the shard's `weights_vol.commit()`, so the second run of a prompt hits.
  - `--lingbot-fast-load` (`LINGBOT_FAST_LOAD=1`): threads (`LINGBOT_READ_AHEAD_THREADS`, default 8) read the VAE and DiT files, plus T5 unless `--lingbot-fast-t5` is on, into the page cache while the pipeline loads; T5 is built on the meta device and its state dict loaded with `mmap=True, assign=True`, skipping upstream's fp32 random init of ~5.7B parameters (same parameter values; falls back to the upstream loader on any error).
  - `--lingbot-fast-y` (`LINGBOT_FAST_Y=1`, session mode): the image conditioning `y` is encoded only up to the latents the rollout has reached, keeping the VAE encoder's causal cache across steps, instead of the whole horizon (248 latents, 989 frames for `--max-total-frames 961`) at every reset. Same encoder calls on the same inputs; only the pointwise `conv1` runs per extension, so values can differ only by cuDNN kernel choice for a different tensor length.
  - `--lingbot-t5-gpu`: T5 on the GPU (upstream's default; same as `LINGBOT_T5_CPU=0`). Changes the text embeddings at bf16 rounding level versus the CPU path, so it is a separate arm, not part of `--lingbot-fast`. Adds about 11 GB of VRAM, held for the rest of the process.
  - `--lingbot-fast-dit` (`LINGBOT_FAST_DIT=1`): the DiT is built with its parameters on the meta device (accelerate's `init_empty_weights`, as diffusers' `from_pretrained` does), each safetensors tensor is copied to the GPU in its file dtype (fp32 on disk, about 75 GB for the 14B) and cast to bf16 there, `LINGBOT_DIT_LOAD_THREADS` shards at a time (default 4), then assigned with `load_state_dict(assign=True)`. Upstream (`load_dit_model` -> diffusers) casts every tensor on the CPU with torch's CPU thread count. Values: fp32 to bf16 is round-to-nearest-even on CPU and CUDA alike, so every finite weight gets the same bits; `tests/test_lingbot_fast_dit.py` checks the loader bit for bit against diffusers' `from_pretrained` and against wan's non-config steps on the CPU. Every parameter must come from the files, else it falls back to the upstream loader (also on any error). Peak extra VRAM during the load is a few fp32 tensors. Verified on the 14B checkpoint (H100): the same `dit checksum` as the upstream loader and `dit verify 16/16 ... ok` (`smk14-gc-fastdit-c10-v1` vs `smk14-gc-fastdit-ctl-c10-v1`), so it is part of `--lingbot-fast`; the flag still works alone. Warm containers (`warm_app.py`) load in `@modal.enter` with default flags, so they use the upstream loader.
  - `--lingbot-cpu-threads[=N]` (`LINGBOT_CPU_THREADS=N|auto`): `torch.set_num_threads` for the process, `auto` = CPUs the container may use (affinity, capped by the cgroup quota). Set per `main()` call; an arm without it restores the starting count. Upstream leaves torch's default, which is 1 on Modal without the `cpu` input (see "Run speed"). CPU T5 reductions may split differently across threads, so embeddings can change bits; it is a separate arm, not part of `--lingbot-fast`, the T5 disk cache identity includes the count, and an arm whose count differs from the previous arm's drops the pipe's in-memory prompt embeddings (`partition_t5_memory`), so every arm encodes at its own count. Threads help only if the container has the cores: pair it with the `cpu` workflow input (`PWA_MODAL_CPU`, Modal's `cpu=` for the generation containers; empty = Modal's default, unchanged). `warm=on` ignores `cpu` (the warm classes request no CPU).
  - `--lingbot-dit-checksum` (`LINGBOT_DIT_CHECKSUM=1`): after the load, `[lingbot] dit checksum <sha256> (<n> tensors, <s>)` over every parameter's bits, computed on the GPU; with `--lingbot-fast-dit` also `[lingbot] dit verify k/n sampled tensors bit-identical to the CPU cast` (first and largest tensor of each shard). Diagnostics only.
  - Always on: one `[lingbot] cpu {...}` line per load with `os.cpu_count()`, affinity, cgroup quota, usable CPUs, `OMP_NUM_THREADS`/`MKL_NUM_THREADS` if set, and torch's intra-op and inter-op thread counts. With `--lingbot-fast-dit`, `load.dit` splits into `load.dit_fast_build`, `load.dit_fast_tensors` (GB, MB/s) and `load.dit_fast_assign`.
- Weights live in the `pwa-weights` Volume under `/weights/lingbot` (`modal run prefetch_lingbot.py --variant 14b|1.3b`; the workflow does this). Outside the workflow set `PWA_RUNNER=<runner>` when calling `modal run modal_app.py` so the LingBot image is selected.

### Upstream quirks (verified)

- IF third-person gate crashes upstream ("third person" vs "third-person"); `pwa` uses the embedded IF check instead.
- Rollouts with no usable score or gate review are dropped from the mean, not counted as 1.0. `pwa report --strict` counts them as 1.0.
- `run_agent.main()` always exits 0, and agent API errors silently fall back to dataset/WAIT actions. `pwa gen` checks mp4s and warns on agent fallback lines. A bad key gives an open-loop rollout, not an error.
- Wait-only insight tasks always regenerate, even with `--resume`.

### Run speed

Sharding is per family: `pwa/gen.py::shard_tasks()` (mirroring upstream `run_agent`) assigns task `i` of each family to shard `i % num_shards`, and a shard runs its families one after another. So generation wall clock is roughly `sum over families of ceil(n_family / num_shards) * min_per_task + load_per_shard`, and shards beyond the largest family get no work. `modal_app.py` maps each shard to its own GPU container (`gen_shard.starmap`) with no cap in code.

- One family per dispatch (`tasks` input listing that family's tasks, `num_shards` = number of tasks) gives one task and one model load per GPU. This is how dev arms are run; no code change was needed.

#### Scenes and attribution

Every `experiment` run that generated videos publishes its rollouts: scored, gen-only (the workflow fetches the Modal volume for this), capped smoke and screening-judge runs; `fake_runner` pipeline tests never. The "Publish scenes" step runs `pwa media EXP --out DIR --base-url URL --release-url URL --report-name NAME --site-url U [--screening JUDGE]`, which re-encodes each rollout to 480p H.264 (`TASK.mp4`, no audio, faststart) with a poster frame (`TASK.jpg`) and writes `EXP.json`: per task the family, mean, status, the verifier's reason (the judge's own text, often Chinese) and the asset URLs, plus run-level `scored` (official verifier passes exist), `max_chunks`, `action_source`, `branch` and `labels` (capped, not scored, screened by MODEL, replayed dataset moves). An unscored run's tasks have no mean or reason and status `not scored`; a screening run's scores never enter the manifest. It also writes `SCENES.md`, the play-link table the workflow appends to the step summary and the report. `pwa media` also writes `RELEASE_NOTES.md`, crediting the model from the run's `meta.json` runner (`MODELS` in `pwa/media.py`; add an entry for a new runner), and publishes nothing for `fake_runner` pipeline tests. The step uploads the clips to a GitHub Release `run-EXP` (created at the run's commit, never marked latest; a rerun clobbers the assets) whose notes carry the attribution and license. The commit step (`.github/scripts/scenes_to_main.sh`, called from the scored, screening and gen-only commit steps) copies `EXP.json` to `results/media/` on main and adds the run to `results/media/index.json` (with `scored` and `labels`; entries without them are official scored runs). The release notes say "not scored by the official PlayWorld verifier" for unscored runs and list the labels. The site's Scenes section reads both like the CSV, and `pages.yml` bundles `results/media` as a fallback. The step is `continue-on-error`, and the gen-only fetch, install and commit steps are too, so a media failure never fails the job or loses the scored row. The step body is `.github/scripts/publish_scenes.sh`. An unscored run (screening judge, gen-only) never replaces official scored Scenes of the same EXP: `publish_scenes.sh` reads main's `results/media/EXP.json` first and skips the release upload and notes when it is scored or unreadable, and `python -m pwa.media to-main` (in `scenes_to_main.sh`) refuses the same downgrade and checks every file before writing, so a failure never commits a manifest without its index entry. Time budget: the Validate step sets `MEDIA_DEADLINE` (job start + 340 min, the job's 350-min `timeout-minutes` less a 10-min reserve for the commit, marker and artifact steps); the gen-only fetch and Publish run under `timeout` to it and are skipped with a warning when under 2 min remain, so a long generation still ends `generated` inside the job cap (without scenes). A Modal gen-only run deletes the fetched rollouts after Publish, so its artifact stays empty as before (the videos stay on the volume). The Scenes picker marks unscored and capped runs, shows the labels as badges, and defaults to the newest official scored run without labels (else the newest run); `?scenes=EXP&scene=TASK` opens that one rollout with the player loaded, and each card has a "Link to this scene".

### Testing tiers and the adoption rule

- **Smoke tier:** 2 or 3 targeted tasks with the flag on, read from `gen.log` (the `[lingbot]` lines and the flag counters) and the action logs, not from scores. It answers "did the flag fire and did nothing break".
- **Decision tier:** all 6 dev tasks of the target family, 2 seeds, official judge, against the shared main baseline at the same seeds.
- **Adoption rule:** a task cell (one task at one seed) moves only when the mean of its judge passes changes by a full point. A flag is adopted only if the gain repeats on both seeds and no gate that passed in the baseline fails. Read it with `pwa cells`. The baseline showed two passes on the same video disagreeing by 0.5 or more on 10 of 24 tasks, so smaller per-task moves and family-mean thresholds are inside judge noise.
- Reported claims still need a closed-loop run scored by Gemini 3.1 Pro over 2 or more passes, with a delta of at least 2x the pass std.
